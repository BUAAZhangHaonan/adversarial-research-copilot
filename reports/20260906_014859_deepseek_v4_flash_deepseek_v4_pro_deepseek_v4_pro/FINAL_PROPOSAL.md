# FINAL_PROPOSAL.md

## 1. Problem and scope

### 1.1 Problem statement

Long-horizon LLM agents that use explicit external memory (notes, RAG stores, databases) fail on delayed, evidence-combining tasks. When an end-task answer is wrong, the failure may originate at **construction time** (the memory record was wrong/incomplete when written) or at **retrieval time** (a correct memory record existed, but the agent selected or used the wrong record later).

Without an instrumented protocol, end-task accuracy cannot separate these two causes. This proposal builds and tests such a protocol.

### 1.2 Research question

Can construction losses and retrieval losses in an explicit-memory agent be **separately attributed**, and can that attribution be **validated by injected ground-truth faults**, within a 5-day execution budget?

### 1.3 Scope

**In scope**

- One LLM agent with one explicit memory store.
- Synthetic episodic tasks where each episode has atomic ground-truth facts.
- Write-time and read-time instrumentation.
- Counterfactual replay with one stage fixed.
- Fault injection at construction or retrieval.

**Out of scope**

- Implicit/in-context memory, hidden weights, model fine-tuning.
- Human memory claims or cognitive theory.
- Multiple memory architectures / scaffold engines.
- Production-grade benchmarks or generalizable leaderboards.

### 1.4 Success criterion

By Friday, we will have a single table reporting, over at least 60 episodes:

- construction-failure precision/recall under injection,
- retrieval-failure precision/recall under injection,
- rescue-difference between construction-fix and retrieval-fix for naturally occurring failures,
- and one negative-control result proving the protocol does not over-attribute failures to an injected stage when the true injected stage is the other stage.

If the attribution protocol cannot distinguish injected construction faults from injected retrieval faults at precision and recall ≥ 0.70, the protocol fails its validation criterion and we report the fallback path in Section 6.

## 2. Method specification

### 2.1 Agent and memory

Fixed components (do not change mid-experiment unless recorded as a confound):

- **Backbone model:** one API-accessible LLM, e.g., GPT-4o-mini or comparable. Use identical temperature/sampling settings for all runs.
- **Memory schema:** a JSON store of records. Each record has:
  - `record_id`,
  - `source_evidence_id`, pointing to one or more atomic facts,
  - `text`: a free-text summary generated by the agent,
  - `write_time`,
  - `read_only`: fixed field for replay editing.
- **Memory operations:** exactly two agent-callable tools:
  1. `write_record(evidence_ids, text)`
  2. `query_memory(query) -> list[record_ids]` followed by reading the selected records.
- **Task executor:** a deterministic harness that presents events, accepts tool calls, and asks terminal questions.

### 2.2 Episode structure

Each episode contains:

- **Events:** 30 events. Each event includes exactly 4 atomic facts. Facts are randomly generated but constrained to a fixed schema, e.g., `Client <ID> has [allergy|medication|preference|appointment] <value>`.
- **Terminal question:** requires combining evidence from 2–4 different events. The correct answer is a unique ground-truth fact string.
- **Distractor events:** events whose facts are never needed for the terminal question.

### 2.3 Construction-stress condition

Two conditions, assigned per episode:

- **Low construction stress:** `write_record` may copy event facts verbatim from the visible event text.
- **High construction stress:** the event text is shown only as a compressed paraphrase that requires the agent to expand it accurately into structured facts, and the agent is limited to 10 words per fact field.

Implementation detail: if compression causes parse failures, that is counted as a construction failure only if the eventual stored record is wrong; parse failures are logged as mechanical errors and excluded from causal attribution counts.

### 2.4 Retrieval-stress condition

Two conditions, assigned per episode:

- **Low retrieval stress:** immediately after all events, the terminal question is asked; no intervening tasks.
- **High retrieval stress:** after all events, the agent performs 10 unrelated arithmetic filler tasks before the terminal question. The memory store additionally contains 20 irrelevant decoy records written by the harness between the final event and the terminal question.

### 2.5 Full factorial

We run a \(2 \times 2\) design:

| Condition | Construction stress | Retrieval stress | Episodes |
|---|---|---|---|
| A | Low | Low | 15 |
| B | High | Low | 15 |
| C | Low | High | 15 |
| D | High | High | 15 |

Total = 60 episodes.

We do **not** claim that these stressors cleanly isolate stages. Stressors are just ways to generate naturally occurring failures. Attribution comes from instrumentation and replay, not from condition labels.

### 2.6 Instrumentation

The harness records, for every episode and every write:

- **T0 audit at write time.** A deterministic auditor compares the `text` in the written record against the source event facts. The check is exact-substring / structured-field equality, not LLM judgment.
  - `T0_pass` = all source facts required by that write are present verbatim.
  - `T0_fail` = one or more required facts are absent, wrong, or extra.
- **T1 audit at retrieval time.** The harness knows the ground-truth terminal fact. At query time, it checks:
  - `T1_retrieval_pass` = the record containing the ground-truth terminal fact is in the top-3 returned records and is selected by the agent.
  - `T1_retrieval_fail` = otherwise.

Important: T1 pass/fail is measured **only on records that already passed T0**. If a record failed T0, it is excluded from T1 evaluation.

### 2.7 Failure classification

For each wrong terminal answer, classify using the audit logs:

- **Construction loss:** the record that should have contained the terminal fact had `T0_fail`, OR no such record was written.
- **Retrieval loss:** the correct record passed T0 but had `T1_fail`.
- **Both:** T0_fail AND T1_fail occurred on the relevant path.
- **Neither / other:** audits pass but terminal answer is wrong. This is logged and counted as attribution failure of the protocol.

### 2.8 Counterfactual fork-and-fix replay

For every naturally occurring wrong episode:

1. **Replay with construction-fix:** use the same event sequence and the same agent, but before retrieval, replace all records that failed T0 with oracle-correct records generated from ground truth. Leave all retrieval dynamics unchanged.
2. **Replay with retrieval-fix:** use the same event sequence and the same agent, but keep original records exactly as written. Before the terminal question, inject an oracle retrieval step: the correct record is placed at the top of the retrieved list and marked as selected. Do not change any other behavior.
3. **Define rescue:** an episode is rescued by construction-fix if the terminal answer changes from wrong to correct after construction-fix. Same for retrieval-fix.

A construction-loss claim is supported if construction-fix rescues at least 5 more episodes than retrieval-fix among episodes classified as construction-only. A retrieval-loss claim is supported similarly in the opposite direction.

### 2.9 Fault-injection validation

Generate **60 additional oracle-correct episodes** (15 per factorial cell condition, same stress protocol). Then inject exactly one fault per episode:

- **Construction fault:** modify one written record before T0 audit so that it fails T0, while preserving the agent’s retrieval behavior afterward.
- **Retrieval fault:** leave all records correct, but after the agent writes its query, replace the top-k retrieved list with a list that excludes the correct record.

We pre-register the gold cause of each injected episode. The attribution protocol must recover that gold cause.

### 2.10 Negative control

In the fault-injection set, include 10 additional episodes where the injected fault is **none**: all records are correct and retrieval is not manipulated. The protocol must classify these as **no construction loss and no retrieval loss**. If the protocol reports any stage-specific loss in more than 1 of these 10 negative-control episodes, the protocol is invalid and the fallback path in Section 6 applies.

## 3. Evaluation protocol

### 3.1 Primary metrics

For naturally occurring failures:

- **Construction-fix rescue count**: number of initially wrong episodes made correct by construction-fix.
- **Retrieval-fix rescue count**: number of initially wrong episodes made correct by retrieval-fix.
- **Construction-only rescue differential**: construction-fix rescue count minus retrieval-fix rescue count among episodes classified as construction-only.
- **Retrieval-only rescue differential**: retrieval-fix rescue count minus construction-fix rescue count among episodes classified as retrieval-only.

For injected episodes:

- **Construction fault precision**: among episodes the protocol labels as construction-only, fraction whose gold cause is construction.
- **Construction fault recall**: among episodes whose gold cause is construction, fraction labeled construction-only by the protocol.
- **Retrieval fault precision**: analogously.
- **Retrieval fault recall**: analogously.
- **Negative-control false-label rate**: fraction of the 10 no-fault episodes labeled as having either construction or retrieval loss.

### 3.2 Pre-registered validation thresholds

The protocol is considered validated only if **all** thresholds below are met:

| Metric | Threshold |
|---|---|
| Construction fault precision | ≥ 0.70 |
| Construction fault recall | ≥ 0.70 |
| Retrieval fault precision | ≥ 0.70 |
| Retrieval fault recall | ≥ 0.70 |
| Negative-control false-label rate | ≤ 0.10 |

If any threshold is not met, report the protocol as not validated and follow Section 6.

### 3.3 End-task abstention control

For all episodes, record three mutually exclusive terminal outcomes:

- `correct`
- `abstained` (agent explicitly says it cannot answer)
- `wrong` (agent gives a wrong, non-abstaining answer)

Report all rescue counts separately for `wrong` episodes. If an intervention changes `wrong` into `abstained`, that is **not** counted as a rescue.

### 3.4 Confound check

At the end of the experiment, verify that construction stress and retrieval stress did not produce identical failure signatures. We pre-register this test:

- Compare the T0_fail rate in low vs high construction stress.
- Compare the T1_fail rate (among T0-pass records) in low vs high retrieval stress.

If high construction stress raises T0_fail by fewer than 5 percentage points, or high retrieval stress raises T1_fail by fewer than 5 percentage points, then the stress manipulation was weak. We report this as a **manipulation-check failure** and do not claim the stress decomposition is meaningful.

### 3.5 Required negative control experiment

The negative control is already in the fault-injection set (Section 2.10). It is mandatory. If the negative-control false-label rate exceeds 0.10, the attribution protocol is not valid.

## 4. Compute/data budget

### 4.1 Total episodes

| Type | Count |
|---|---|
| Natural episodes (2×2) | 60 |
| Fault-injection episodes | 60 |
| Negative-control no-fault episodes (included in the 60 above) | 10 |
| **Total initial runs** | **120** |

### 4.2 Replay runs

Every naturally occurring wrong episode triggers 2 replay runs (construction-fix, retrieval-fix). Expected wrong rate under stress conditions is conservatively 50%, so expected replay runs are \(60 \times 50\% \times 2 = 60\).

### 4.3 LLM API call budget

Per episode, estimate at most 25 LLM calls:

- 30 events × 1 write call? No. To stay within budget, do **not** call the LLM to write each event separately. Instead, batch event processing into segments of 5 events. This yields 6 write calls per episode plus 1 terminal question call plus occasional query calls. Total LLM calls per episode ≤ 10.

Total LLM calls estimate:

\[
(120 + 60) \times 10 = 1800 \text{ calls}
\]

At 100 calls/minute, this is 18 minutes of API time. Add retries and logging overhead: total wall-clock API time ≤ 1 hour.

### 4.4 Time budget (5 days)

- Day 1: build harness, memory schema, event generator, audit functions.
- Day 2: implement stress conditions, replay logic, fault injection.
- Day 3: run natural episodes and replays; collect raw logs.
- Day 4: run fault-injection set and negative-control episodes.
- Day 5: compute metrics, run confound checks, write final report.

### 4.5 Storage budget

All logs are JSONL. Estimated < 50 MB. Store in a local directory with a schema version field. No GPU required.

## 5. Kill criteria

Stop the current line of work and either fix the root cause or revert to the fallback path if any of these occur:

1. **Harness bug identified mid-run:** if event generation, audit checks, or replay logic is found to mutate records incorrectly in more than 2 episodes, stop and fix before continuing. Do not analyze buggy data.
2. **API/model instability:** more than 20% of episodes fail due to API errors, timeouts, or malformed tool calls. Do not proceed until retry/backoff is stable.
3. **Stress manipulation fails:** after first 20 episodes, if T0_fail rate does not differ between low and high construction stress by at least 5 percentage points, stop and redesign the construction-stress implementation.
4. **Validation threshold failure:** on the fault-injection set, if either construction fault recall or retrieval fault recall is below 0.50 after the first 30 injections, do not continue collecting more injections until the attribution logic is debugged.
5. **Endpoint impossible:** if construction-fix or retrieval-fix replay cannot be implemented without changing the other stage by design (i.e., contamination), stop and use the fallback path in Section 6.

## 6. Fallback path

### 6.1 If protocol fails validation (recommended)

If the attribution protocol cannot meet precision/recall thresholds, do **not** report the causal attribution results as valid. Instead:

- Publish and report only:
  1. T0_fail / T1_fail rates per stress condition,
  2. construction-fix rescue count,
  3. retrieval-fix rescue count,
  4. negative-control false-label rate.
- Label the outcome as: “stage-separated **correlational** audit results; causal attribution was not validated.”
- State explicitly that construction-vs-retrieval rescue claims are unsupported.

### 6.2 If counters require no replay

If fault-injection validation succeeds but natural failures are too rare (<10 wrong episodes), then:

- Switch the natural-failure analysis to the fault-injection episodes only.
- Report fault-injection precision/recall as the primary evidence that the protocol is valid.
- Do not report construction/retrieval rescue differentials on natural failures beyond descriptive counts.

### 6.3 If stress manipulation is confounded

If construction and retrieval stress cannot be manipulated independently, run only the low-stress/low-stress and high-stress/high-stress cells. Then the experiment answers only:

> Under combined stress, what fraction of failures are attributable to construction vs retrieval via fault-injection-validated replay?

This loses the \(2 \times 2\) stress-decomposition claim but preserves the attribution-protocol contribution.

### 6.4 Absolute fallback deliverable

If all experimental lines fail, produce a 2-page protocol-validation report containing:

- exact schema,
- exact audit predicates,
- fault-injection implementation,
- negative-control result,
- and per-cell failure counts.

This deliverable is useful even without causal claims because it operationalizes memory-stage auditing for other researchers.

## 7. Claims we will and will not make

**Will make if thresholds are met**

1. For this agent and this synthetic task, construction loss and retrieval loss can be measured separately with write-time and read-time audits.
2. Single-stage counterfactual replay changes rescue outcomes in the expected direction for a pre-registered fraction of episodes.
3. The attribution protocol distinguishes injected construction faults from injected retrieval faults at precision and recall ≥ 0.70.
4. Adding fault-injection negatives reduces false attribution: in no-fault episodes, false stage labels are ≤ 10%.

**Will not make**

- We will not claim construction vs retrieval is a new cognitive distinction.
- We will not claim either stressor isolates a memory stage.
- We will not claim any improvement in end-task accuracy.
- We will not claim C5-style abstention metrics are novel; they are explicit controls.

## 8. Exact task-generation example

Event (low stress, visible verbatim):

```
Event 12:
Client A-104: allergy = penicillin
Client A-104: appointment = 2026-03-02 10:00 with Dr. Okafor
Client B-209: preference = window seat
Client C-331: medication = metformin
```

Write tool call by agent:

```
write_record(evidence_ids=["A-104"], text="Client A-104: allergy = penicillin; appointment = 2026-03-02 10:00 with Dr. Okafor")
```

T0 auditor:

- Required facts for this write: `allergy=penicillin`, `appointment=2026-03-02 10:00 with Dr. Okafor`.
- If both appear verbatim in `text`, T0_pass = true.

Terminal question example:

```
Which medication does the client whose allergy is penicillin currently take?
```

This requires joining `Client A-104 allergy` with a later event stating `Client A-104 medication = metformin`. Answer: `metformin`.

This example is not evaluable by an LLM judge; it is checked by string equality against the ground truth.
