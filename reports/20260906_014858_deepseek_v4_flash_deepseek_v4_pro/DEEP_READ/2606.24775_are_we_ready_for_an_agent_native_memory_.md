# Extraction: “Are We Ready For An Agent-Native Memory System?” (Zhou et al., 2026)

**Nature of the paper (for calibration):** This is an *evaluation/benchmark study*, not a proposal of one new memory system. Its “claims” are comparative empirical statements about 12–14 existing agent-memory systems + baselines on NLP/agent benchmarks. The supplied full text contains **no dedicated Limitations section**, **no enumerated future-work list**, and only a one-paragraph Conclusion. I flag this explicitly below so absence of author-stated limitations/outlook is not mistaken for my omission.

Labeling: **[Author-stated]** = the paper’s own text/results. **[Inference]** = my analytical judgment, clearly separated.

## (1) VERIFIED CLAIMS

### 1.1 Evaluation protocol common to all claims

**[Author-stated] Conditions (data, scale, protocol):**
- Systems: “12 representative memory systems and two reference baselines (Long Context and Embedding RAG)” (§4.1). Table 1’s taxonomy actually lists 14 named configurations (MemoChat, Mem0, MEM1, MemAgent, MemTree, Zep, Mem0^g, Cognee, LightMem, SimpleMem, MemOS, MemoryOS, A-MEM, Letta) across three families (Sequential Context; Structural Topological; Multi-Paradigm Hybrid).
- Workloads: the abstract claims “five benchmark workloads spanning 11 datasets”; within the supplied text only four workload families are concretely described: LoCoMo (long-conversation QA), LongMemEval (multi-session memory; scored with MemoryAgentBench metrics including a “GPT-5.4-based LLM Judge”), DB-Bench (derived from LifelongAgentBench, database procedural execution), and LongBench (long-context QA with Short/Medium/Long buckets) (§4.1, §4.4). The exact composition of “11 datasets” is **not spelled out in the provided text** — a gap for the reader.
- Metrics: category-level Exact Match (EM) and Answer F1 (LoCoMo, unweighted mean); Substring EM, ROUGE-L F1/Recall, GPT-5.4 LLM-Judge Accuracy (LongMemEval); EM + Task Success Rate (DB-Bench); Accuracy (LongBench); Recall@K over gold evidence (LoCoMo, RQ2); normalized utility + amortized operation latency (RQ5) (§4.1–§4.5).
- Scale bounds observed in figures: LongMemEval session-history bins run roughly 38–54 sessions (n = 9–30 per bin, Figure 10b); LoCoMo evidence-distance bins run 1–5 to 26–31 session gaps (§4.2, Figure 8).
- Backbones: Qwen3-8B, DeepSeek-Chat, GPT-5.4-mini, GPT-5.4; backbone ablation performed only on LoCoMo and only for 6 memory configurations (§4.3, Figure 9).
- Compute/token budget: **not reported anywhere in the supplied text** (e.g., no API/GPU hours, no per-run token cost, no number of seeds).

**[Inference] Controlled variables:** The authors control for (i) evidence temporal distance (binning), (ii) context length (LongBench buckets), (iii) history size (session bins), (iv) LLM backbone (Figure 9), and (v) module choice in Section 5 “controlled variants that modify one module at a time.” **Not controlled/reported:** random seed replication, statistical significance, variance/confidence intervals, implementation hyperparameter tuning per system, or the version/date of each third-party system’s code — all absent from the text.

### 1.2 Cross-workload effectiveness (RQ1)

**[Author-stated]** “No single memory system dominates all workloads” (§4.1, O1, Figure 7):
- LongMemEval: Zep leads at 48.0 LLM-Judge Accuracy; Cognee reaches 35.3 ROUGE-L F1.
- LoCoMo (exactness): MemOS reaches 11.5 EM.
- DB-Bench: **Long Context (the no-memory baseline)** achieves 48.20 EM; MemoChat reaches 55.40 Task Success Rate.
- “Among methods with full workload coverage, MemoryOS and MemOS remain closest to the frontier overall.”
- EM is informative for short, canonical answers but “insufficient when correctness depends on paraphrastic synthesis or executable success” (§4.1, O2).

**[Inference] What this does NOT rule out:** The “no universal winner” conclusion is conditional on these 5 workloads/11 datasets. The fact that a *no-memory baseline* wins DB-Bench EM is an internal hint that some benchmark slices measure something memory systems do not optimize. Domain coverage is thin for code/API agents, web navigation, multi-agent or tool-intensive sessions (only DB-Bench is “agentic execution”); rankings on other agent workloads could differ. Judge-based scores on LongMemEval rest on a single GPT-5.4-family judge, whose preferences could advantage certain answer styles.

### 1.3 Retrieval fidelity (RQ2)

**[Author-stated] Protocol:** LoCoMo source-level gold evidence; “Recall@K, where a hit requires the top-K retrieved source-id groups to contain the annotated gold evidence”; plus Recall@10 across six evidence-distance bins (§4.2). Eight systems evaluated.
- SimpleMem: highest Recall@1 = 39.0.
- A-MEM: 69.5 / 85.9 on Recall@5 / Recall@10; MemTree: 59.7 / 80.5, stable as evidence distance grows.
- Flat Embedding RAG: ~95 Recall in the nearest bin (1–5), collapses to ~0 after bin 11–15 (Figure 8).
- Author interpretation: retrieval is “not mainly a top-1 ranking problem, but an evidence-completion problem”; explicitly linked/hierarchical structure helps “scattered or temporally distant” evidence, flat similarity only “short-range access” (Finding 2).

**[Inference] Not ruled out:** These results are single-benchmark (LoCoMo). Recall@K over session-id groups rewards systems that return whole sessions/parent nodes (A-MEM/MemTree are hierarchical by design), so part of the measured advantage may reflect the *granularity of what counts as a retrieved unit* rather than retrieval quality per se. The flat RAG baseline uses no reranking or query expansion, so the gap partly reflects RAG configuration, not a theoretical limit of flat retrieval.

### 1.4 Update robustness (RQ3)

**[Author-stated] Protocol:** (1) Update-robustness comparison on LongMemEval Knowledge Update and Temporal Reasoning slices, plus LoCoMo Temporal; 11 memory systems + 2 baselines (Table 2). (2) Backbone ablation: 6 settings × 4 LLMs on LoCoMo, only the backbone varying (Figure 9).
- Knowledge Update (LongMemEval): Zep leads, 44.4 Substring EM / 36.8 ROUGE-L F1.
- Temporal Reasoning (LongMemEval): Cognee leads, 18.7 / 35.8.
- LoCoMo Temporal: MemOS best EM (8.9); Cognee best Answer F1 (28.1). Letta (MemGPT) is weakest on several slices (e.g., 0.0 EM on LoCoMo Temporal; 5.7 ROUGE-L F1 on Knowledge Update).
- Backbone robustness: “Answer F1 generally rises under stronger generators, yet the overall ordering changes only modestly”; MemOS stays strongest across Qwen3-8B / DeepSeek-Chat / GPT-5.4-mini / GPT-5.4 (32.2 / 41.2 / 38.6 / 41.2 Answer F1). Only notable reversal: A-MEM overtakes MemTree under GPT-5.4-mini and GPT-5.4 (§4.3, O5, Figure 9).

**[Inference] Not ruled out:** The “robust across backbones” claim is demonstrated on **one benchmark (LoCoMo), 6 of 14 configurations, 4 backbones**; it says nothing about backbone × memory interaction on LongMemEval, DB-Bench, or LongBench. Update robustness is tested on single-round fact revisions in benchmark conversations, not on long chains of successive contradictory updates or multi-user concurrent writes. “Hallucinations of the past” is an inference label the authors attach to stale-fact outputs; the eval does not separate *retriever returned the stale fact* from *generator preferred the stale fact despite retrieval*.

### 1.5 Long-horizon stability (RQ4)

**[Author-stated]** (Figure 10; §4.4):
- LongBench: SimpleMem is nearly flat Short→Medium (35.2 → 34.9 Accuracy), whereas Long Context drops 42.6 → 19.0, showing long prompts alone accumulate distractors.
- LoCoMo: Embedding RAG falls from 37.1 to 7.4 Answer F1 as evidence gap widens; Cognee, MemOS, MemoryOS remain substantially higher across bins.
- Author conclusion (Finding 4): longer horizons punish flat/raw-context/dense approaches; relational or hierarchical structure preserves distant fact connectivity.

**[Inference] Not ruled out:** The tested “long horizon” is modest by production-agent standards (years of daily use, millions of memory objects): LongMemEval bins cap around 54 sessions; LoCoMo around 31-session gaps; some bins have only n=9–12 queries (Figure 10b). Long-term *operational* stability — index bloat, consolidation cascades, drift over months — was not measured longitudinally.

### 1.6 Operational cost (RQ5)

**[Author-stated] Protocol:** “unified time-overhead traces recorded by our runner”; Avg. Operation Latency/Query = construction + query time amortized; Normalized Utility = mean of 6 min–max normalized quality metrics from LoCoMo and LongMemEval runs; 8 systems (§4.5).
- LightMem: Normalized Utility 48.3 at 3.67 s/query; MemTree: 63.5 at 15.9 s (the strongest efficiency frontier).
- MemoChat 28.0 at 15.4 s; Mem0 21.4 at 35.9 s; A-MEM 57.7 at 17.9 s.
- MemoryOS reaches 82.0 utility only at 28.6 s; Cognee and Zep exceed 84 utility only at 116.5 s and 155.1 s.
- LongBench latency: LightMem 17.3 s; MemTree 116.7 s; Mem0 / MemoChat / MemoryOS / A-MEM rise to 374.2 / 460.2 / 490.0 / 552.1 s.
- Author conclusion (Finding 5): efficiency is governed by **maintenance scope** (localized vs. global reorganization), not by structure per se.

**[Inference] Not ruled out:** Latency results are environment- and engine-specific (vector/graph DB choice, hardware, API variability), and no p50/p99, concurrency, or scale-vs-latency curves are given. No measurement of LLM token cost during extraction/consolidation, which for LLM-heavy systems (Mem0, A-MEM, Zep) may dominate real dollar cost and could invert some “utility per cost” conclusions.

### 1.7 Fine-grained module ablations (Section 5)

**[Author-stated] Verified module-level results:**
- **M1 Representation (Table 3):** LightMem User-Only Raw beats Summary and Compressed on all four metrics (LoCoMo EM 24.2 / Ans F1 38.9; LongMemEval Substring EM 26.0 / ROUGE-L 31.4). Compressed stays close on LoCoMo (23.6 / 38.6) but collapses on LongMemEval Substring EM (10.7 vs 26.0). Deeper MemTree gives only marginal gains over flat (18.7 vs 18.2 EM; 30.9 vs 29.9 ROUGE-L). Mem0’s default vs Graph Store backend differs little (3.2→3.0 EM; 6.2→6.5 Ans F1), though the paper does not interpret this row in prose.
- **M2 Extraction (Table 4):** MemoChat *Heuristic Topic* ≥ *LLM Topic* on LongMemEval (10.7 vs 7.3 Substring EM) with LoCoMo about equal. MemOS *Fast Memorize* massively beats *Fine Memorize* on LoCoMo (25.5 vs 2.5 EM; 40.8 vs 5.0 Ans F1) while *Fine Memorize* is better on LongMemEval (22.3 vs 20.7 Substring EM) — the authors read this as “fine-grained LLM-based extraction can yield modest precision gains but substantially degrade multi-hop reasoning” (§5.2, O9).
- **M3 Retrieval/Routing (Table 5):** A-MEM Hybrid-Balanced > Hybrid Sparse-Leaning (24.6 vs 23.0 Ans F1). SimpleMem *Planning Only* > *No Planning* and > *Planning + Reflect* (20.7 Ans F1 / 90.6 Recall vs 18.7/86.4 and 20.0/88.6) — “extra deliberation may weaken rather than improve routing.”
- **M4 Maintenance (Figure 12):** MemoryOS Conservative-Merge improves over default (23.2→23.5 Ans F1; 22.4→22.8 Substring EM); Delayed-Flush degrades it (20.6 / 19.5); MemoChat forced single-topic summaries underperform its default multi-topic setting.

**[Inference] Not ruled out:** Each module claim rests on 1–2 host systems and one operationalization of each technique (e.g., one summarization prompt, one “Fine Memorize” schema, one similarity threshold). Effects of 0.3–0.5 metric points (Conservative-Merge, Deeper Tree) are presented as findings without significance testing or repeated runs; these particular deltas are likely within noise. The M2 result could mean “this particular fine-grained extractor was poorly matched to LoCoMo,” not “fine-grained extraction is generally harmful for reasoning.” The M1 result is conditional on the quality of the LLM-generated summaries tested — better summarizers could narrow the Raw-Summary gap.

### 1.8 Highest-level claims that overreach the evidence

**[Inference]** The Introduction’s headline findings (❶–❻) state some results more categorically than the experiments support: “effective memory systems remain robust across LLM backbone variants” (tested on 1 benchmark), “graph-based methods handle knowledge updates most reliably” (true on LongMemEval KU, but MemOS/MemoryOS — hybrid, not graph — are the overall frontier systems for full coverage), and “popular fact-extraction plugins… struggle with targeted overwrites” (demonstrated for Mem0 specifically, not fact-extractor plugins generally). These are author framings, but the reader should attach the protocol qualifications from §1.1–1.6 to them.

## (2) AUTHOR-STATED LIMITATIONS

**[Author-stated] The submitted full text contains no explicit Limitations or Threats-to-Validity subsection, and the Conclusion (§6) states no caveats of its own.** This absence is itself the key finding here. The closest author-stated restrictive statements are:

1. **Scope restriction (explicitly stated, near-verbatim):**
   - “We focus on memory-centric systems, rather than task-specific agent frameworks where memory is an auxiliary module” (§1, para. 2).
   - “We focus on system-level memory over textual, structured, and even parametric representations” (§1, para. 2).
   - The taxonomy definitions in §2 explicitly exclude stateless RAG and context engineering (“Distinction from RAG and Context Engineering,” §2) and argue agent-memory workloads differ from traditional OLTP/OLAP (“Distinction from Traditional Database Workloads,” §2).

2. **Coverage admissions embedded in results (implicit, close paraphrase):**
   - “Among methods with **full workload coverage**, MemoryOS and MemOS…” (§4.1) — implies not every system ran on every workload, so some head-to-head comparisons are partial.

   - Table 2/Figure 9 evaluate only subsets of systems per experiment; §5 states that component experiments used “representative strategies within each technique component.”
